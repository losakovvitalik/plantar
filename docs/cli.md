# CLI

Запуск внутри монорепозитория: `cd apps/cli && pnpm start <команда> [опции]`

## Сборка и публикация

CLI собирается в один самодостаточный файл: `pnpm build` → `dist/index.cjs` (esbuild, все workspace-пакеты и зависимости внутри). Пакет публикуется в npm как `@plantar/cli` (`pnpm publish` соберёт автоматически); после установки `npm install -g @plantar/cli` доступна команда `plantar`. На установленный из npm пакет опирается workflow «Деплой при коммите» (см. [features.md](features.md)) — до первой публикации шаг `npm install -g @plantar/cli` в GitHub Actions будет падать.

## Общие опции подключения

Есть у всех команд:

| Опция | Описание |
| --- | --- |
| `--host <host>` | адрес сервера (обязательно) |
| `--user <user>` | имя пользователя (обязательно) |
| `--port <port>` | SSH-порт, по умолчанию `22` |
| `--key <path>` | путь к приватному ключу |
| `--password <pass>` | пароль (если без ключа); безопаснее передать его в `PLANTAR_PASSWORD` |
| `--host-key <fingerprint>` | ожидаемый ключ сервера, `SHA256:…`; можно передать в `PLANTAR_HOST_KEY` |

Нужно указать либо `--key`, либо пароль.

Пароль в `--password` виден в списке процессов и остаётся в истории команд,
поэтому его лучше передавать переменной окружения `PLANTAR_PASSWORD` —
она используется, когда `--password` не указан.

### Проверка сервера

У каждого сервера есть собственный опознавательный ключ. Если по адресу
отвечает не тот сервер (подменённый DNS, чужая Wi-Fi-сеть, переданный другому
клиенту IP), ключ будет другим — и всё, что уходит на сервер, включая пароль,
достанется чужой машине.

`--host-key` (или `PLANTAR_HOST_KEY`) задаёт ожидаемый ключ: если сервер
предъявит другой, подключение прерывается до входа, пароль не отправляется.
В CI это обязательный параметр — иначе деплой пойдёт на любую машину,
ответившую по адресу.

Отпечаток и тип ключа печатаются при подключении без `--host-key` — именно эти
два значения и нужно закрепить. Сверить отпечаток на самом сервере можно
командой `ssh-keygen -lf` по файлу того ключа, который сервер предъявил (обычно
`/etc/ssh/ssh_host_ed25519_key.pub`, но у сервера может быть ключ другого типа):

```bash
PLANTAR_HOST_KEY=SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx \
  PLANTAR_HOST_KEY_TYPE=ssh-ed25519 \
  plantar deploy --host 1.2.3.4 --user root --key ~/.ssh/id_ed25519
```

Кроме отпечатка вида `SHA256:…` принимается целая строка вывода `ssh-keygen -lf`
(`256 SHA256:… root@host (ED25519)`) — отпечаток берётся из неё — и сам отпечаток
без префикса `SHA256:`. Значение любого другого вида считается опечаткой, а не
сменой ключа: запуск останавливается с отдельной ошибкой ещё до подключения.

Необязательная переменная `PLANTAR_HOST_KEY_TYPE` называет тип закреплённого
ключа целиком — `ssh-ed25519`, `ssh-rsa`, `ecdsa-sha2-nistp256`,
`ecdsa-sha2-nistp384` или `ecdsa-sha2-nistp521` (у RSA все алгоритмы дают ключ
типа `ssh-rsa`). Тогда при рукопожатии этот тип запрашивается первым, и сервер,
у которого появился ключ другого типа, всё равно предъявляет закреплённый; без
переменной тип выбирает ssh-библиотека. Флага у неё нет: её записывает «Деплой
при коммите» рядом с отпечатком (см. [features.md](features.md)), а при ручной
настройке её значение берётся из того же сообщения о непроверенном ключе.

Значение другого вида — например `ed25519` вместо `ssh-ed25519` — запрошено быть
не может: запуск не останавливается, но выводит предупреждение с этим значением
и списком известных типов, а дальше идёт так же, как без переменной. Без
предупреждения такая опечатка выглядела бы иначе: сервер с ключами нескольких
типов предъявил бы не закреплённый ключ, и запуск упал бы позже — как при смене
ключа сервера. В журнале GitHub Actions на месте значения будет `***`:
переменная приходит из секрета репозитория, а значения секретов в журнале
скрываются, поэтому исправлять нужно сам секрет `PLANTAR_HOST_KEY_TYPE`.

## Команды

### `ls`

Список директорий на сервере.

- `--path <path>` — какую директорию смотреть, по умолчанию `.`

### `info`

ОС, ресурсы (CPU, RAM, диск) и установленные инструменты (node, pnpm, pm2, nginx, certbot). Показывает, поддерживается ли сервер (Ubuntu 22.04/24.04).

### `setup`

Устанавливает недостающие инструменты: Node.js 22 (NodeSource), pnpm, pm2, nginx, certbot. Уже установленные пропускает — можно запускать повторно.

### `deploy`

Деплоит проект на сервер. Каждая версия загружается в `/var/www/<name>/releases/<метка времени>`, симлинк `/var/www/<name>/current` указывает на рабочую версию. Что происходит, зависит от `type` в `plantar.json`:

- `static` — сборка выполняется локально (`buildCommand`), на сервер загружается только папка `buildDir`;
- `node` — код загружается на сервер, зависимости устанавливаются там, приложение запускается через pm2; если в `package.json` есть скрипт `build` (NestJS, Strapi, TypeScript), перед запуском выполняется серверная сборка;
- `next` — как `node`, но перед запуском выполняется серверная сборка;
- `bot` — как `node`, только без nginx и порта.

Для сайтов и приложений настраивается nginx, при указанном `domain` выпускается SSL-сертификат. Идемпотентна.

- `--project <dir>` — папка проекта с `plantar.json`, по умолчанию текущая

### `logs`

Логи nginx по сайту (access и error). Скачанное сохраняется локально как снапшот.

- `--project <dir>` — папка проекта с `plantar.json`, по умолчанию текущая
- `--lines <n>` — сколько последних строк показать, по умолчанию `50`

### `history`

Локальная история деплоев: когда, какой проект, на какой сервер, успех или ошибка, путь к логу. Не требует подключения к серверу (и опций подключения).

- `--project <name>` — фильтр по имени проекта

## Локальные данные

Всё хранится в директории данных ОС (macOS: `~/Library/Application Support/plantar`, Linux: `~/.local/share/plantar`):

```text
history.json              # история деплоев
logs/<name>/
  deploy-<время>.log      # полный лог каждого деплоя (пишется даже при ошибке)
  nginx-access.log        # последний снапшот серверных логов
  nginx-error.log
```

## plantar.json

Лежит в корне деплоимого проекта:

```json
{
  "name": "my-app",
  "buildCommand": "pnpm build",
  "buildDir": "dist",
  "domain": "example.com"
}
```

| Поле | Описание |
| --- | --- |
| `name` | имя сайта (обязательно): строчные латинские буквы, цифры, дефис; определяет `/var/www/<name>` |
| `type` | тип проекта: `static`, `node`, `next` или `bot`; по умолчанию `static` — приложение без явного `type` задеплоится как статический сайт |
| `runtime` | рантайм бота: `node` или `python`, по умолчанию `node`; для `python` зависимости ставятся из `requirements.txt` в venv |
| `packageManager` | пакетный менеджер: `npm`, `pnpm`, `yarn` или `bun`, по умолчанию `npm` |
| `legacyPeerDeps` | только для npm: ставить зависимости с `--legacy-peer-deps` (конфликт версий зависимостей); по умолчанию выключено |
| `buildCommand` | команда сборки (`static` — локально, `next` и `node` со скриптом `build` — на сервере), по умолчанию `npm run build` |
| `buildDir` | папка с результатом сборки (только для `static`), по умолчанию `dist` |
| `startCommand` | команда запуска приложения (`node`, `next`, `bot`), по умолчанию — start-скрипт пакетного менеджера (`npm start`); для бота на `python` значения по умолчанию нет — поле обязательно. Статические сайты её не используют |
| `port` | порт Node.js-приложения (1–65535); подбирается автоматически при первом деплое. GUI-приложение записывает выбранный порт в `plantar.json`, CLI — нет: при деплое через CLI укажите `port` в конфиге явно, иначе он будет меняться при каждом деплое |
| `domain` | домен сайта; если не указан — сайт отвечает по IP сервера, без HTTPS |

Пример: [examples/react-demo-app](../examples/react-demo-app/plantar.json).
