# Функции проекта

Краткое описание основных функций проекта и какие файлы за них отвечают.

Plantar — local-first инструмент деплоя приложений на Ubuntu-серверы (22.04/24.04) для не-программистов. Две оболочки — desktop GUI (`apps/desktop`, Electron + React) и CLI (`apps/cli`) — используют общую логику из пакетов:

| Пакет | Назначение |
| --- | --- |
| `packages/ssh` | SSH-соединение (ssh2): exec, стриминг вывода, загрузка директорий tar-архивом, `shellQuote` |
| `packages/core` | Вся deploy-логика: проверка и подготовка сервера, деплой, env, логи, удаление |
| `packages/config` | Схема `plantar.json` (zod), чтение/запись, автоопределение типа проекта |
| `packages/storage` | Локальные данные: серверы, проекты, история, настройки, логи, ключи |

## SSH-подключение

`packages/ssh/src/index.ts` — класс `SshConnection`: `exec` (команда → stdout/stderr/код), `execStream` (живой вывод с остановкой), `uploadDirectory` (пакует папку в tar.gz, загружает одним файлом по SFTP и распаковывает на сервере; поддерживает исключения), `listDirectories`. Keepalive раз в 15 секунд.

- Пул соединений (desktop): `apps/desktop/src/main/ssh-pool.ts` — живое соединение переиспользуется между операциями, закрывается после 2 минут простоя. Пока соединение живо, пароль повторно не запрашивается (`isConnected`).

## Серверы и авторизация

- Добавление сервера: `apps/desktop/src/main/index.ts` (`addServer`) + `apps/desktop/src/renderer/src/components/add-server-dialog.tsx`. Два режима: по ключу и по паролю.
- Режим «ключ»: `apps/desktop/src/main/ssh-setup.ts` — генерирует пару ed25519 (`ssh-keygen`), по паролю устанавливает публичный ключ в `authorized_keys`, проверяет вход по ключу и только потом сохраняет сервер. Приватный ключ шифруется системным keychain (`safeStorage`), fallback — файл 0600; есть разовая миграция старых незашифрованных ключей.
- Режим «пароль»: пароль не сохраняется, запрашивается диалогом при каждом новом подключении (`password-dialog.tsx`).
- Ключ сервера: `packages/ssh` проверяет его при каждом подключении (`hostVerifier`, до аутентификации), политику задаёт `apps/desktop/src/main/host-keys.ts` — доверие при первом подключении, отдельно для каждого типа ключа (как `known_hosts`). Тип и отпечаток предъявленного ключа сохраняются в `ServerRecord.hostKeys`, дальше сервер обязан предъявлять тот же ключ этого типа; иначе соединение падает с `HostKeyRejectedError`, а UI показывает отдельное состояние «сервер отвечает не так, как раньше» вместо обычной ошибки подключения. Типы из записи уходят в начало списка алгоритмов, которые приложение предлагает при рукопожатии (`knownHostKeyTypes` → `algorithms.serverHostKey`, так же OpenSSH поступает с типами из `known_hosts`): и сервер, обзаведшийся ключом другого типа, и новый порядок предпочтений в ssh-библиотеке всё равно приводят к ключу из записи. Ключ типа, которого в записи нет, не принимается — сравнить его не с чем, и по такому ключу сервером мог бы назваться кто угодно.
- Если сервер переустанавливали, ключ можно заменить, не удаляя сервер: кнопка в баннере «сервер отвечает не так, как раньше» открывает подтверждение (`identity-changed-banner.tsx` → `trust-host-key-dialog.tsx` → IPC `servers:trustHostKey` → `trustNewHostKey` в `apps/desktop/src/main/host-keys.ts`). Диалог показывает отпечаток, которым сервер отвечает сейчас, и тип этого ключа (`hostKeyTypeLabel` в `apps/desktop/src/renderer/src/lib/host-key-type.ts` печатает его как панель хостинга и `ssh-keygen -lf` — `ED25519`, `RSA`, `ECDSA`, а не именем алгоритма из рукопожатия): в панели по строке на каждый тип ключа, и сравнивать отпечаток нужно со строкой того же типа. По подтверждению диалог записывает отпечаток в `ServerRecord.hostKeys` вместо всех прежних (после переустановки старых ключей у сервера не остаётся); сервер и его проекты остаются на месте. Отказ или закрытие диалога не меняют ничего. Отпечаток в Secrets репозитория при этом не обновляется: диалог перечисляет проекты сервера, у которых настроен деплой при коммите, — им нужно настроить его заново. Такие проекты узнаются по пометке `ProjectRecord.deployOnCommit` (`deployOnCommitProjectNames` в `apps/desktop/src/renderer/src/lib/deploy-on-commit.ts`); серверу без таких проектов это предупреждение не показывается. Записям, сделанным до появления пометки, её проставляет тот же диалог: перед тем как назвать проекты, он спрашивает у main пометки заново (IPC `github:backfillDeployOnCommit` в `apps/desktop/src/main/ipc/github.ts`), и тот ищет в репозиториях git-проектов сервера файл workflow, который оставляет за собой удачная настройка (`hasDeployWorkflow` в `apps/desktop/src/main/github-actions.ts` — contents API с `?ref=<ветка проекта>`). Пометка ставится только по найденному файлу и никогда не снимается: без входа в GitHub, без файла в репозитории, а также если репозиторий удалён или не отвечает, запись остаётся как была — GitHub тут не может ни сломать подтверждение ключа, ни выдать предупреждение на пустом месте. Переименованный или переданный другому владельцу репозиторий на старый адрес отвечает редиректом, за которым запрос идёт сам: файл находится по новому адресу, и пометка там уместна — репозиторий тот же, ключ сервера по-прежнему лежит в его Secrets.
- При добавлении сервера ключ фиксируется на первом же подключении и переиспользуется остальными (установка ключа, проверка входа), чтобы подмена в середине настройки не сохранилась в записи.
- У серверов, добавленных до появления проверки, отпечатка в записи нет: он записывается при следующем подключении, повторно добавлять сервер не нужно. Записи, сделанные до появления типов (`ServerRecord.hostKeyFingerprint` — отпечаток без типа), продолжают работать: принимается только этот отпечаток, и первое же совпавшее подключение переносит его в `hostKeys` вместе с типом.
- CLI записей не ведёт: ожидаемый отпечаток передаётся флагом `--host-key` или переменной `PLANTAR_HOST_KEY` (см. `docs/cli.md`).

## Проверка сервера

`getServerInfo` в `packages/core/src/index.ts` — ОС (поддерживается ли), CPU, RAM, свободный диск, версии инструментов (node, pnpm, pm2, nginx, certbot, python+venv). UI: `status-tab.tsx`.

## Подготовка сервера

`setupServer` в `packages/core/src/index.ts` — устанавливает недостающее: Node.js 22 (NodeSource), pnpm, pm2, nginx, certbot, python3+venv+pip. Идемпотентна: установленное пропускает. В GUI пока не выведена — доступна через CLI `setup`.

## Проекты и plantar.json

`packages/config/src/index.ts`:

- Схема конфига: `name`, `type` (static | node | next | bot), `runtime` (node | python), `packageManager`, `buildCommand`, `buildDir`, `startCommand`, `port`, `domain`. Regex на `name` и `domain` заодно защищают от shell-инъекций.
- `detectProjectConfig` — автоопределение по файлам проекта: пакетный менеджер по lockfile, фреймворк (Vite, CRA, Next.js, Express/Fastify/NestJS/…, grammY/Telegraf, aiogram/python-telegram-bot), тип проекта и команды сборки/запуска.
- Добавление проекта в GUI: выбор папки → предзаполненная форма настроек → создание `plantar.json` (`apps/desktop/src/main/index.ts`: `pickProjectFolder`, `addProject`; UI `project-settings-dialog.tsx`). Имя проекта проверяется на уникальность в пределах сервера.
- Настройки проекта редактируются в том же диалоге; после сохранения предлагается деплой в один клик (`app.tsx`).

## Деплой

`deployProject` в `packages/core/src/index.ts`, три сценария по `type`:

- **static** — локальная сборка (`buildCommand`, env-переменные с сервера подставляются в окружение сборки), загрузка в staging-папку и публикация как новой версии; nginx раздаёт статику из `current` (без домена — default_server по IP).
- **node** — загрузка кода (без node_modules, .git, .env), установка зависимостей на сервере, запуск через pm2 (ecosystem-конфиг, автозапуск после перезагрузки), автоподбор свободного порта 3001–3999 с закреплением в `plantar.json`, проверка что приложение отвечает по HTTP, nginx как reverse proxy.
- **next** — как node, но после установки зависимостей выполняется серверная сборка `buildCommand`; старая версия остаётся рабочей, если сборка падает. Переменные проекта копируются в `.env` до сборки, затем приложение запускается через pm2 и проксируется nginx.
- **bot** (Telegram-бот, runtime node или python) — то же без nginx и порта; для python — venv + `pip install -r requirements.txt`; проверка что pm2-процесс стабильно живёт.

Структура на сервере: каждая версия деплоится в `/var/www/<name>/releases/<метка времени>`, симлинк `/var/www/<name>/current` указывает на рабочую версию (хранится 5 последних, `finalizeRelease`/`switchCurrent`/`pruneReleases` в core). Прежняя плоская структура `/var/www/<name>` заменяется управляемой при первом же деплое. pm2-конфиг каждой версии лежит внутри её папки — процесс при деплое пересоздаётся из новой папки. Для node/next симлинк переключается только после того, как новая версия ответила по HTTP. Если новая версия не запустилась или не ответила (для ботов — процесс нестабилен), прежняя рабочая версия автоматически возвращается в pm2 (`restorePreviousRelease` в core), деплой завершается ошибкой, а в логе видны и сбой, и результат восстановления; при первом деплое (включая импортированные приложения) восстанавливать нечего — чужие процессы не трогаются.

Общее: HTTPS через certbot/Let's Encrypt при наличии `domain` (сертификат не перевыпускается зря), идемпотентность повторного деплоя, подробный лог каждого шага. Перед записью конфига nginx проверяется, не объявлен ли домен в чужом конфиге (`findDomainConflicts` в `packages/core/src/discover.ts`, точное совпадение `server_name`); найденный конфликт отключается тем же механизмом, что при takeover, — до запуска certbot, чтобы 443-блок лёг в конфиг Plantar. После настройки nginx/SSL выполняется смоук-проверка публичного адреса с самого сервера (curl с ретраями, `verifySiteAvailable`): 2xx/3xx/4xx — «сайт доступен», 502/503/504 или отсутствие ответа — вместо этого предупреждение с кодом ответа (деплой не падает). Оркестрация в desktop: `runDeploy` в `apps/desktop/src/main/index.ts`, UI `deploy-tab.tsx` (живой лог + системное уведомление о результате).

## Возврат предыдущей версии (откат)

`rollbackProject` + `listReleases` в `packages/core/src/index.ts`: у сайтов переключается симлинк `current`, у приложений pm2 пересоздаётся из папки предыдущей версии (с проверкой ответа по HTTP; если у версии был другой порт, nginx перенастраивается на него). Цель возврата выбирает `pickRollbackTarget` по версии, из которой реально запущен pm2-процесс (`pm2 jlist`), а не только по симлинку: если после неудачного деплоя процесс разошёлся с `current` (или пропал), возвращается сам `current` — последняя рабочая версия. Кнопка «Вернуть предыдущую версию» — на вкладке «Деплой» (IPC `deploy:rollback`, оркестрация `runRollback` в `apps/desktop/src/main/index.ts`); записи отката попадают в историю с пометкой (`kind: "rollback"`). Для проектов, задеплоенных до появления структуры версий, откат недоступен — приложение объясняет почему. У внешних (импортированных) проектов возврат версии работает иначе — по git-истории на сервере, см. «Импорт существующего приложения».

## Импорт существующего приложения

Сценарий для серверов, где приложения крутились до подключения Plantar. Ничего не устанавливает на сервер:

- **Обнаружение** — `discoverApps` в `packages/core/src/discover.ts`: `pm2 jlist` (имя, папка, entrypoint, статус, пути логов, PORT из env), `ss -tlnp` + `ps -eo pid,ppid` (слушающие порты, в том числе у дочерних процессов `npm start`), `nginx -T` (домен → upstream-порт, файл конфига, пути логов; поддерживаются upstream-блоки), git-remote папки приложения (`origin`, ветка, подпапка в монорепозитории; ssh-адреса приводятся к https — `normalizeGitUrl`). Тип предлагается автоматически: python-скрипт → бот, папка `.next` → Next.js, есть порт → node, иначе бот.
- **UI** — кнопка «Найти приложения» на экране сервера открывает диалог «Найдено на сервере» (`discover-apps-dialog.tsx`, IPC `server:discover`): список приложений с предзаполненными полями (название, тип, домен, порт) и фактами с сервера (папка, pm2-процесс, статус, найденные env-файлы); уже добавленные проекты не показываются. «Добавить» создаёт внешний проект (IPC `projects:import`).
- **Внешний проект** (`external` в `ProjectRecord`, `packages/storage`) — Plantar управляет им сразу: живые логи идут по фактическим путям pm2/nginx процесса, переменные и статус работают. Пометка «внешний» постоянна и снимается только при явном переносе под управление Plantar. Пока источник кода не привязан, настройки живут в записи проекта (plantar.json нет). Если у приложения на сервере нашёлся git-remote, вкладка «Деплой» предлагает «Подключить репозиторий» (IPC `projects:linkRepo`): репозиторий клонируется как обычный git-проект (с веткой и подпапкой монорепозитория), иначе — «Указать папку с кодом» (IPC `projects:linkFolder`). В обоих случаях plantar.json создаётся из подтверждённых при импорте настроек поверх автоопределённых; для переноса под управление Plantar привязка источника кода обязательна.
- **Бережный деплой** (`deployExternalInPlace` в `packages/core/src/external.ts`, оркестрация `runExternalInPlace` в `apps/desktop/src/main/index.ts`) — деплой внешнего проекта воспроизводит то, что команда делала бы руками, и не имеет скрытых побочных эффектов: `git checkout <ветка> && git pull --ff-only` в исходной папке приложения (checkout заодно лечит отвязанный HEAD после возврата версии), установка зависимостей менеджером по lockfile на сервере, сборка при наличии скрипта `build` и `pm2 restart` под прежним именем процесса — строго после успешной сборки, поэтому упавшая сборка не трогает работающий процесс. nginx, порты, SSL и структура `releases` не затрагиваются. Ошибки git (грязная папка, разошедшаяся история) отдаются читаемым текстом, `git reset --hard` не выполняется никогда. Без git-репозитория в папке приложения бережный деплой честно недоступен. Переменные внешнего проекта читаются и сохраняются прямо в `.env` его папки (`readExternalEnv` / `writeExternalEnv`; при нескольких env-файлах редактируется базовый, остальные не трогаются) — хранилище Plantar на сервере для них не создаётся.
- **Git-версии и возврат** — вкладка «Версии» (`versions-tab.tsx`, IPC `versions:external` → `getExternalVersions`) показывает последние коммиты ветки с сервера. Возврат версии — честный повторный деплой выбранного коммита: `git checkout --detach` + установка + сборка + перезапуск (IPC `deploy:rollbackExternal`), с подтверждением, что это займёт время. Пока развёрнут не последний коммит ветки, вкладки «Версии» и «Статус» показывают индикатор «развёрнута не последняя версия» (`behindTip`) с объяснением про отвязанный HEAD; следующий обычный деплой возвращает ветку. После деплоя, упавшего на проверке «приложение не отвечает»/«процесс нестабилен» (коды `app-not-responding` / `process-unstable` из `packages/core/src/process-checks.ts`), вкладка «Деплой» предлагает кнопку «Вернуть предыдущую версию» — повторный деплой последнего успешно развёрнутого коммита. Кнопка появляется только после бережного деплоя (вид прогона `deploy`): после неудачного переноса под управление Plantar (вид `migrate`) прежний pm2-процесс уже снят, и возврат по нему невозможен. У внешних проектов без git возврата версий нет вовсе — с коротким объяснением, а не задизейбленной кнопкой.
- **Веб-сервер на месте, без переноса** — две явные подтверждаемые операции дополняют собственный nginx-конфиг импортированного приложения, не заставляя переносить его под управление Plantar. «Настроить HTTPS» на вкладке «Статус» (IPC `external:setupHttps` → `setupExternalHttps` в `packages/core/src/index.ts`) запускает `certbot --nginx` для домена из настроек: certbot сам дополняет тот конфиг, который уже обслуживает домен, и сам проверяет и перезагружает nginx; Plantar файлы не переписывает. «Вести отдельный журнал» в карточке «Посещаемость» (IPC `external:enableAccessLog` → `enableExternalAccessLog` в `packages/core/src/nginx-external.ts`) добавляет одну строку `access_log` в server-блоки конфига, которые проксируют на порт приложения и своего журнала не имеют (`access_log off` уважается — такие блоки не трогаются): перед записью файл копируется в `/var/www/.plantar/nginx-backups/`, результат проверяется `nginx -t`, при любой ошибке исходный файл возвращается на место; существующие строки не меняются и не переформатируются. Обе операции показывают в диалоге, что именно изменится, и доступны только пока проект внешний.
- **Явный перенос под управление Plantar** — кнопка «Перевести под управление Plantar» на вкладке «Деплой» открывает диалог подтверждения (`migrate-project-dialog.tsx`) со списком того, что изменится: переезд кода в `/var/www/<имя>/releases`, пересоздание процесса под новым именем, отключение прежнего конфига nginx, перенос переменных из `.env` в хранилище Plantar — и предупреждением, что данные в старой папке (базы, загрузки) не переносятся. Только после подтверждения запускается прежний takeover-деплой (IPC `projects:migrate` → `runDeploy(..., migrate)`; `takeover` в `DeployOptions`): прежний pm2-процесс снимается, прежний конфиг nginx отключается (симлинк в sites-enabled удаляется, обычный файл переносится в sites-available; конфиг вне sites-enabled не трогается — об этом пишется в лог), приложение переходит на структуру `releases/current`, пометка «внешний» снимается — дальше проект живёт как обычный. Файлы старого приложения на сервере не удаляются.

## Деплой из GitHub-репозитория

Второй источник проекта наряду с локальной папкой (`add-project-dialog.tsx` — выбор источника):

- **Публичные и приватные репозитории.** По вставленной ссылке приложение делает `git clone` в локальную папку `reposDir()` (`~/Library/Application Support/plantar/repos/<id>`) и дальше запускает обычный пайплайн деплоя из папки — серверу доступ к GitHub не нужен. Клонирование, обновление, список веток и чтение коммита — `apps/desktop/src/main/git.ts` (через `execFile("git", …)`, токен передаётся заголовком `http.extraHeader`, а не в URL). `plantar.json` хранится как untracked-файл в клоне и переживает обновление.
- **Выбор ветки.** В форме — выпадающий список веток (`git ls-remote --symref`), по умолчанию выбрана дефолтная ветка репозитория.
- **Папка проекта в репозитории (монорепозитории).** Опционально можно указать подпапку внутри репозитория, если проект лежит не в корне (`subdir` в `ProjectRecord`; по умолчанию — корень). Выбор через нативный диалог в корне клона (`projects:pickSubdir`), настройки переопределяются автоопределением по выбранной папке. Эффективная папка проекта = `path` + `subdir`; git-операции идут по корню клона.
- **Redeploy.** Для git-проектов кнопка деплоя всегда сначала обновляет клон (`git fetch` + checkout + `reset --hard origin/<branch>`), затем деплоит. В карточке проекта (вкладка «Деплой») виден хеш и сообщение задеплоенного коммита (`deployedCommit` в `ProjectRecord`).
- **Авторизация GitHub (Device Flow).** Вход без собственного backend, только по `client_id` (`apps/desktop/src/main/github.ts`). Токен шифруется системным keychain (`safeStorage`, файл `github-token.enc`), приватные репозитории клонируются с ним. В настройках — подключённый аккаунт и кнопка выхода (`settings-dialog.tsx`, `github-login-dialog.tsx`).

## Деплой при коммите (GitHub Actions)

Кнопка «Настроить деплой при коммите» на вкладке «Коммиты» (git-проекты): после одного клика каждый push в ветку проекта деплоит его на сервер без участия приложения. UI — `setup-ci-dialog.tsx`, IPC `github:setupActions`, оркестрация — `setupGithubActions` в `apps/desktop/src/main/index.ts`, работа с GitHub API — `apps/desktop/src/main/github-actions.ts`:

- Генерируется **отдельный deploy-ключ** ed25519 (личный ключ пользователя не используется), публичная часть добавляется в `authorized_keys` сервера (`installPublicKey`).
- Приватный ключ, адрес сервера и его ожидаемый ключ записываются в Secrets репозитория (`PLANTAR_SSH_KEY`, `PLANTAR_HOST`, `PLANTAR_PORT`, `PLANTAR_USER`, `PLANTAR_HOST_KEY`, `PLANTAR_HOST_KEY_TYPE`) через GitHub API; значения шифруются публичным ключом репозитория (sealed box, `libsodium-wrappers`). Хранение ключа в GitHub Secrets — осознанное исключение из local-first, см. README («Принципы»).
- В Secrets попадает отпечаток того самого подключения, которым настройка ставила deploy-ключ: сервер по нему только что проверен, а без пиннинга деплой из CI уходил бы на любой сервер, ответивший по адресу.
- Рядом с отпечатком записывается тип ключа (`PLANTAR_HOST_KEY_TYPE`): workflow передаёт его CLI переменной окружения, и тот просит этот тип первым — так же, как приложение просит типы из записи сервера. Иначе тип выбирала бы ssh-библиотека на CI, и сервер, обзаведшийся ключом более предпочитаемого типа, отвечал бы там другим ключом: приложение продолжало бы работать, а деплой при коммите падал бы на проверке. Секрет, записанный прежней версией приложения (без типа), продолжает работать по-старому — тип снова выбирает библиотека.
- В ветку проекта одним коммитом (Git Data API) добавляются `.github/workflows/plantar-deploy.yml` и `plantar.json` (в клоне он untracked, поэтому в репозитории его обычно нет). Workflow на push ставит `@plantar/cli` из npm и запускает `plantar deploy` с ключом из Secrets; для static-проектов с pnpm/yarn/bun ставится нужный пакетный менеджер.
- Требуются вход в GitHub (Device Flow, scope `repo`) и право пуша в репозиторий. Повторный запуск идемпотентен по файлам (без изменений — без коммита), но создаёт новый deploy-ключ и перезаписывает Secrets.
- Успешная настройка помечает проект в записи (`ProjectRecord.deployOnCommit`) — это единственный локальный след того, что репозиторий хранит ключ сервера. По пометке диалог доверия новому ключу называет проекты, которым после переустановки сервера нужно настроить деплой при коммите заново (Secrets продолжают хранить прежний ключ, см. «Серверы и авторизация»). Настройки, сделанные версиями приложения без этой пометки, тот диалог опознаёт по оставшемуся в репозитории `.github/workflows/plantar-deploy.yml` и проставляет пометку сам — настраивать деплой при коммите заново ради этого не нужно. Файл в репозитории один, поэтому два проекта из одного репозитория и одной ветки (монорепозиторий по подпапкам) по нему не различаются: пометку получают оба, хотя рабочий деплой при коммите в таком репозитории всё равно может быть только у одного из них.
- Ограничение: деплой из GitHub Actions пишет историю на CI-машине, поэтому в истории и бейджах коммитов приложения такие деплои пока не видны; отображение планируется (например, чтение статусов запусков workflow через API).

## Переменные окружения

Хранятся на сервере в `/var/www/.plantar/env/<name>.env` (не в папке релиза — деплой их не затирает; права 600). Функции `readProjectEnv` / `writeProjectEnv` в `packages/core/src/index.ts`. При деплое: для static подставляются в локальную сборку, для Next.js копируются в `.env` перед серверной сборкой, для node/bot — рядом с кодом перед запуском; локальные `.env`-файлы из проекта на сервер не загружаются. UI: `env-tab.tsx` — редактор с импортом из локальных `.env`-файлов проекта (IPC `env:*` в `apps/desktop/src/main/index.ts`); вставка многострочного текста в поле имени или значения разбирается как env-файл и добавляет сразу несколько переменных (комментарии сохраняются). Исключение — внешние (импортированные) проекты: их переменные читаются и сохраняются прямо в `.env` папки приложения на сервере (`readExternalEnv` / `writeExternalEnv` в `packages/core/src/external.ts`), хранилище Plantar для них не создаётся; при переносе под управление Plantar содержимое `.env` переезжает в хранилище.

## Логи

- Живой стрим (desktop): `logStreamCommand` в `packages/core/src/index.ts` (tail -F, переживает ротацию) + `execStream`; два источника — приложение (pm2 out/error) и nginx (access/error). IPC `logs:streamStart/Stop` в `apps/desktop/src/main/index.ts`, UI `logs-tab.tsx` (пауза, раздельные каналы «Вывод/Ошибки»). Просмотренные nginx-логи по настройке сохраняются локально.
- Снапшот nginx-логов (CLI): `getSiteLogs` в core + `saveServerLogSnapshot` в storage.

## Статус приложения и мониторинг

Вкладка «Статус» проекта показывает данные самого приложения (`app-status-tab.tsx`, IPC `metrics:*`), а не сервера:

- **Здоровье процесса** — `pm2ProcessHealth` в `packages/core/src/status.ts`: статус, время запуска, число перезапусков, текущие CPU/память процесса из `pm2 jlist`. Для static-сайтов вместо карточки процесса — пояснение, что отдельного процесса нет.
- **Статусы в сайдбаре** (IPC `server:appStatuses`, хук `use-app-statuses.ts`) — pm2-процессы сервера одним запросом плюс живая HTTP-проверка сайтов (`checkSitesRespond` в `packages/core/src/status.ts`): запрос к публичному адресу с самого сервера, как в смоук-проверке после деплоя. Проверяются работающие приложения (кроме ботов) и статика, которая хотя бы раз успешно деплоилась; живой процесс при неотвечающем сайте — статус `unresponsive` («Сайт не отвечает»). Снимок кэшируется для мгновенного показа при следующем запуске.
- **Посещаемость** (node/next/static) — `getTrafficStats` в `packages/core/src/monitoring.ts`: GoAccess на сервере разбирает access-лог nginx вместе с ротированными копиями (~2 недели), графики (shadcn chart + recharts, `components/ui/chart.tsx`): запросы/посетители по дням, распределение по часам, счётчики ошибок, популярные страницы. Без GoAccess вкладка предлагает установить его на экране сервера. Какой журнал читать, решает `trafficLogPath` в `apps/desktop/src/main/traffic-log.ts`: у проекта под управлением Plantar это `/var/log/nginx/<имя>.access.log` из шаблона nginx, у импортированного — только путь, найденный в его конфиге. Если у проекта Plantar журнала пока нет (не было первого деплоя), вкладка объясняет, что посещения не записываются и журнал появится после первого деплоя (`logMissing` в `TrafficStats`). Если же в конфиге импортированного приложения нет своего `access_log`, посещения идут в общий журнал сервера вперемешку с остальными сайтами — выделить статистику приложения оттуда нельзя, поэтому вкладка объясняет это и деплой не предлагает (`sharedLog` в `TrafficStats`). Если при импорте были найдены конфиг nginx и порт приложения, а своего `access_log` в конфиге нет, карточка предлагает завести отдельный журнал на месте — см. «Веб-сервер на месте, без переноса» в разделе про импорт.

Экран сервера (`server-monitoring.tsx`) — опциональные инструменты мониторинга, устанавливаются по явному выбору пользователя (`installMonitoringTool`, IPC `monitoring:*`; идемпотентно, из репозитория Ubuntu):

- **GoAccess** — статистика посещений, работает только в момент проверки.
- **Netdata** — история нагрузки сервера (CPU/память за час или сутки, `getServerMetrics`, IPC `metrics:server`). При установке привязывается к 127.0.0.1 (запросы идут по SSH, наружу порт не открыт), ML-анализ отключён; конфиг перезаписывается только при свежей установке.

## Фоновый мониторинг и уведомления о падениях

Main-процесс каждые 5 минут (`MONITOR_INTERVAL_MS` в `apps/desktop/src/main/app-monitor.ts`) проверяет приложения на всех серверах той же логикой, что статусы сайдбара (общий сборщик `collectServerAppStatuses`, один SSH-раунд-трип на сервер), и присылает системные уведомления:

- **«Приложение перестало работать»** — только на переходе «работало → упало» и только после подтверждающей перепроверки через 30 секунд (`MONITOR_CONFIRM_DELAY_MS`); пока приложение лежит, повторных уведомлений нет. При восстановлении приходит «снова работает». Клик открывает окно Plantar на проекте.
- **«Сервер не отвечает»** — недоступность сервера по SSH даёт одно уведомление, а не «упали все приложения»; при пропаже собственной сети пользователя монитор молчит (`net.isOnline`).
- Проверки идут только для серверов с ключевой аутентификацией (парольные — пока живо соединение в пуле; пароль не хранится) — экран парольного сервера явно объясняет, что фоновая проверка недоступна. Во время активного деплоя проверки проекта подавляются. Логика переходов — чистая функция `monitor-transitions.ts` с unit-тестами.
- Приложение живёт в трее на всех платформах (`tray.ts`): закрытие окна не завершает процесс, мониторинг продолжается; из меню трея можно открыть окно или выйти. При сне ноутбука цикл останавливается (`powerMonitor`), после пробуждения первая проверка ждёт минуту, чтобы не дать ложных срабатываний.
- Тумблер «Следить за приложениями в фоне» (`notifyOnAppDown` в `AppSettings`, включён по умолчанию) отключает фоновые проверки и уведомления.

## Локализация (i18n)

Весь пользовательский текст (GUI, CLI, деплой-лог, ошибки) переведён на русский и английский:

- `packages/i18n` — общий механизм для Node-кода: текущий язык процесса (`setLanguage`, по умолчанию из локали системы: русская → ru, иначе en) и фабрика `createT(messages)`. Словари живут рядом с кодом: `packages/{core,config,ssh}/src/messages.ts`, `apps/cli/src/messages.ts`, `apps/desktop/src/main/i18n.ts`.
- Renderer (React): `apps/desktop/src/renderer/src/i18n/` — `ru.ts` (эталон ключей), `en.ts`, `index.tsx` (`I18nProvider`, хук `useI18n` → `t(key, params)`). Компоненты не содержат захардкоженных пользовательских строк.
- Язык хранится в настройках (`language` в `AppSettings`, `packages/storage`). Desktop: переключатель в диалоге настроек, применяется сразу, без перезапуска; main-процесс узнаёт о смене через `settings:set`. CLI читает язык из тех же настроек при старте.
