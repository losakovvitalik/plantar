# /ship-review — ревью PR для ship-issue

Аргумент: номер PR (обязателен). Без номера — сообщи об ошибке и остановись.

Ты ревьюишь чужой код. Будь скептичен: каждое утверждение из описания PR проверяй по diff.

Замечания уходят **inline на строки диффа**, а не одним комментарием: тред живёт между раундами и
служит реестром открытых находок. Поэтому у скилла жёсткий порядок фаз — сначала свой взгляд на код,
и только потом чужие выводы.

## 1. Свежий взгляд (треды прошлых раундов НЕ читать)

- `gh pr view <PR> --json title,body,additions,deletions,changedFiles,baseRefName`
- `gh pr diff <PR>` — полный diff. Сохрани его в файл: он нужен на шаге 3 для якорей.
- Есть `Closes #<N>` → `gh issue view <N> --json title,body`. Ревью проверяет и то, что PR решает issue.
- `CLAUDE.md` в корне — его правила учитывать.
- Файлы, где diff непонятен без окружения, читай через `Read` — только нужные фрагменты.

**До конца этого шага не смотри ни комментарии PR, ни существующие треды, ни прошлые ревью.**
Свежесть взгляда — единственная причина, по которой каждый раунд ревьюит новый агент.

Критерии:

1. **Корректность** — решает ли код задачу issue/PR; логические ошибки; неверное использование API и типов.
2. **Читаемость** — имена, сложность, можно ли следовать логике без комментариев.
3. **Поддерживаемость** — жёстко зашитые значения, дублирование, лёгкость будущих изменений.
4. **Производительность** — лишние рендеры, N+1, тяжёлые операции в циклах.
5. **Безопасность** — XSS, инъекции, утечки, логирование чувствительных данных.
6. **Стиль и архитектура** — CLAUDE.md и соглашения проекта (i18n-словари, kebab-case, комментарии по-английски).
7. **Edge cases** — пустые значения, null/undefined, ошибки сети, неожиданный ввод.

Тесты, сборку и тайпчек не запускай.

Про незатронутый код: замечание на pre-existing проблему не поднимать. Но если **изменение делает
существующий код неверным или опасным** — это находка по этому PR, даже когда падает всё в другом
файле. Такие обычно самые ценные, и заанкорить их некуда — им место в теле ревью (шаг 3).

Классификация:
- 🔴 blocker — баг, уязвимость, некорректная логика, нарушение правил проекта; чинить до мержа.
- 🟡 suggestion — улучшение, локальное по последствиям: читаемость, поддерживаемость или
  производительность внутри самого этого кода.
- 🟢 nitpick — мелочь на усмотрение автора.

Граница между 🔴 и 🟡 проходит по заразности, а не по категории. Находка идёт в 🔴, если правка
задаёт образец для будущего кода: дублирует то, для чего в репозитории уже есть общее место;
вводит новый паттерн там, где есть устоявшийся; хардкодит значение, которое дальше будут копировать.
Такой код цитируют следующие PR, и цена растёт с каждым из них. Неудачное имя или микрооптимизация
внутри одной функции остаются 🟡 — их никто не скопирует.

## 2. Разбор прошлых раундов

Только теперь:

```bash
gh api graphql -f query='
query($owner:String!,$repo:String!,$pr:Int!){
  repository(owner:$owner,name:$repo){ pullRequest(number:$pr){
    reviewThreads(first:100){ nodes{
      id isResolved isOutdated path line
      comments(first:10){ nodes{ databaseId author{login} body } } } } } }
}' -f owner=<owner> -f repo=<repo> -F pr=<PR>
```

Владельца и репозиторий бери из `gh repo view --json owner,name`.

Для каждого **нерезолвленного** треда реши по текущему коду, а не по переписке:

- **fixed** — проблемы в коде больше нет. Резолвь тред:
  ```bash
  gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id=<threadId>
  ```
- **accepted** — автор отклонил с обоснованием, и обоснование верное. Ответь в тред согласием и резолвь:
  ```bash
  gh api repos/<owner>/<repo>/pulls/<PR>/comments/<databaseId>/replies -f body='<текст по-английски>'
  ```
- **open** — проблема на месте (или «исправление» её не закрыло). Тред **не резолвить**, ответить в него,
  чем именно текущий код всё ещё плох, и включить находку в JSON шага 4 с её `threadId`.

Понижать серьёзность находки только потому, что её уже обсуждали, нельзя. Если 🔴 после правки
осталась 🔴 — она остаётся 🔴, даже если правка сделала её реже воспроизводимой.

## 3. Опубликовать ревью

Всё, что уходит на GitHub, — **по-английски**.

**Якоря.** Заанкорить можно только строку, попавшую в diff. По сохранённому `gh pr diff` для каждого
файла собери адресуемые строки: в хедере `@@ -a,b +c,d @@` это строки `c … c+d-1` нового файла
(добавленные `+` и контекстные). Предпочитай `+`-строки. Для удалённой строки — `"side": "LEFT"`
и номер в старом файле. Для диапазона — `"start_line"` вместе с `"line"`.

Находка, чью строку заанкорить нельзя (файл вне диффа, строка вне ханка), **не выбрасывается** —
она идёт в тело ревью с явным `path:line` в тексте.

**Запрос.** Собери JSON через `Write` (не через heredoc) и отправь одним вызовом:

```bash
gh api repos/<owner>/<repo>/pulls/<PR>/reviews --input <file.json>
```

```json
{
  "event": "COMMENT",
  "body": "<summary + verdict + находки без якоря, markdown>",
  "comments": [
    { "path": "packages/storage/src/index.ts", "line": 388, "side": "RIGHT",
      "body": "🔴 <problem>\n\n> Suggestion: <fix>" }
  ]
}
```

`event` — **всегда `COMMENT`**. `APPROVE` и `REQUEST_CHANGES` GitHub запрещает на собственном PR,
а PR цикла открыт от того же аккаунта; вердикт живёт текстом в `body`.

**Если пришёл 422** (`line must be part of the diff`) — запрос не прошёл целиком. Не подбирай строки
наугад: повтори один раз с `"comments": []`, перенеся все находки в `body`. Ревью должно быть
опубликовано в любом случае — потерянный раунд хуже, чем ревью без якорей.

Тело ревью:

```markdown
## Review — round <K>

<1–2 sentences: what the PR does>

### Verification of the PR claims
<по строке на каждое проверяемое утверждение из body PR: подтвердилось по diff/коду или нет и чем;
опустить, если проверять нечего>

### Resolved since the previous round
<по одной строке на тред, закрытый на шаге 2; секцию опустить в первом раунде>

### Still open
<находки шага 2 со статусом open, с path:line; опустить, если таких нет>

### New findings
<находки, которым не нашлось якоря, с path:line; остальные — inline>

### Verdict
**Assessment:** Approve / Request Changes

<2–4 sentences: что сделано хорошо, что чинить до мержа>
```

## 4. Финальный ответ

Последнее сообщение заканчивается fenced-блоком `json`, после него — ничего:

```json
{"blockers": [{"file": "path:line", "problem": "...", "suggestion": "...", "threadId": "<id|null>"}],
 "suggestions": [{"file": "path:line", "problem": "...", "suggestion": "...", "threadId": "<id|null>"}],
 "resolved": ["<кратко, что закрыто на шаге 2>"],
 "verdict": "approve" | "request_changes"}
```

`blockers` — только 🔴 (и новые, и оставшиеся открытыми со старых раундов), `suggestions` — только 🟡.
🟢 остаются в ревью и в JSON не попадают. Есть хоть один 🔴 → `"request_changes"`.
`threadId` — `null` для находок без якоря.
